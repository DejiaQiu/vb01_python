# 功能需求单

## 目标
- 明确当前项目的生产部署边界：`report/api` 部署在云端服务器，`monitor` 部署在边缘设备。
- 将“数据处理与诊断计算”默认下沉到边缘设备执行，云端不再依赖本地采集目录或定时批诊断任务作为主生产链路。
- 明确边缘采集模式默认采用“持续采集 + 运行态识别 + 运行段切片 + 段数据判断”，而不是简单的固定时刻抓拍。
- 将云端服务收敛为“接收边缘结果 + 提供查询接口 + 生成报告上下文 + 对接 Dify”的轻编排角色。
- 保留现有在线监控、边缘同步、报告生成、Dify 展示和训练链路的兼容性，不因部署拆分重写算法。

## 背景
- 当前仓库已经存在云边协同雏形：边缘侧有 `elevator_monitor.monitor`、`edge_sync`，云端有 `api/routers/ingest.py` 和 `ingest_store.py`。
- 但当前项目仍保留“云端直接跑 `batch_diagnosis` / `report` 处理 CSV”的主路径，导致云端同时承担数据处理、报告生成和 Dify 集成。
- 用户期望的生产形态是：
- 边缘设备负责采集、边缘计算、缓存和上送。
- 云端服务器负责 Dify、查询接口、结果汇总和展示，不直接承担主数据处理任务。

## 用户场景
- 现场边缘设备连接 `WT-VB01-485` 传感器，持续采集并在本地完成异常检测、诊断计算和状态更新。
- 电梯并非持续运行，若只在固定时间点采样，可能采到长时间静止数据，因此生产采集不能只依赖定时抓取。
- 边缘设备需要在持续采集中识别电梯何时进入运行态，并在一次完整或近完整的运行片段上完成诊断，而不是拿零散静止点直接下结论。
- 云端服务器接收多个边缘设备上送的最新状态、告警事件和可选上下文文件，并向 Dify 或上层平台提供统一查询接口。
- 用户在 Dify 中询问某台电梯当前状态时，默认读取云端保存的边缘最新结果，而不是触发一次新的云端 CSV 诊断任务。
- 当边缘设备临时离线或网络中断时，本地计算仍应继续，待网络恢复后再补传结果。
- 离线 CSV 诊断能力可以继续保留给调试、回放或人工复盘使用，但不再作为生产默认主链路。

## 范围
- 包含：重新定义云端与边缘的职责边界、默认部署方式、主生产链路和数据流向。
- 包含：定义边缘侧“持续采集、运行态识别、运行段切片、段结果固化”的默认策略。
- 包含：把现有 `edge_sync -> ingest -> latest-status/report-workflow` 这条链路明确为生产主路径。
- 包含：收敛云端接口的默认语义，使其主要消费边缘上送的结构化结果，而不是依赖云端本地 CSV 目录。
- 包含：保留现有结构化输出契约，如 `status`、`primary_issue`、`top_candidate`、`watch_faults`、`risk`、`report_markdown_draft`。
- 包含：保留离线 CSV 诊断接口作为辅助能力，但在接口说明、部署说明和 Dify 接入中降级为调试/回放用途。
- 不包含：重写钢丝绳/橡胶圈算法逻辑。
- 不包含：重做训练发布链路。
- 不包含：引入新的外部消息队列、数据库或新的第三方依赖。
- 不包含：强制进行大规模目录迁移或重命名 `report/`、`monitor/` 代码树。

## 实现位置
- `elevator_monitor/monitor/`：边缘运行时继续承担采集、边缘计算、本地状态与同步编排。
- `elevator_monitor/edge_sync.py`：作为边缘到云端的默认上送通道，继续负责队列、重试和幂等投递。
- `elevator_monitor/api/routers/ingest.py` 与 `elevator_monitor/ingest_store.py`：作为云端接收和落盘边缘结果的主入口。
- `elevator_monitor/api/routers/workflows.py` 与相关服务：云端基于已接收结果生成报告上下文和 Dify 输入，不再默认触发云端主诊断。
- `deploy/docker-compose.edge.yml`、`deploy/docker-compose.api.yml` 及相关文档：同步体现新的生产部署职责。
- 测试范围覆盖边缘计算、本地缓存/补传、云端查询与 Dify 报告编排的主链路。

## 接口与输入输出
- 边缘设备仍以现有 `elevator_monitor.realtime_monitor` 或复用现有诊断逻辑的本地任务作为计算入口，输出本地 `health`、`latest status`、`alerts`、运行段文件和可选上下文文件。
- 边缘侧本地数据建议至少分为三层：
- 实时原始帧缓冲，用于连续采集和短时回看。
- 运行段数据文件，用于对一次运行过程做完整判断或复盘。
- 结构化摘要结果，如 `latest_status`、`alert event`、`health`。
- 生产判断默认应基于“运行段”或“满足最小时长/最小样本数的有效窗口”，而不是在固定时刻直接抽一小段未知工况数据。
- 当设备连续采集但电梯处于静止或空闲状态时，系统可以继续保留原始帧或做健康监控，但不应把这类静止数据直接当作有效诊断段。
- 边缘到云端的生产上送入口保持为：
- `POST /api/v1/ingest/heartbeat`
- `POST /api/v1/ingest/alert`
- `POST /api/v1/ingest/context`
- 云端对外查询当前状态的生产入口保持为：
- `GET /api/v1/elevators/{elevator_id}/latest-status`
- `GET /api/v1/elevators/{elevator_id}/alerts`
- `GET /api/v1/alerts/{event_id}`
- 云端对 Dify 或上层平台提供的报告入口，应优先从边缘上送结果构建报告上下文，不要求云端重新跑一次诊断算法。
- `POST/GET /api/v1/workflows/diagnosis-report-latest` 应以云端保存的边缘最新状态为默认输入源。
- `POST /api/v1/diagnostics/batch-run`、`POST /api/v1/diagnostics/rule-engine` 可继续保留，但默认定位为调试、回放、离线验证接口，不作为生产当前状态主来源。
- 云端保存的最新状态输出至少包含：`generated_at_ms`、`received_at_ms`、`status`、`primary_issue` 或等价兼容字段、`top_candidate`、`watch_faults`、`risk`、`latest_alert`、`context`。
- 边缘上送失败时，事件必须先安全落入本地队列，待网络恢复后重试；不能因云端不可用而阻塞边缘主计算。

## 业务规则
- 生产主链路默认改为“边缘计算，云端展示”，而不是“边缘采集，云端主算”。
- 边缘采集不能以“定时到点抓一段数据”作为唯一主策略，因为电梯在该时刻可能不在运行中。
- 边缘设备应持续读取传感器数据，并基于振动活跃度、连续新帧、速度代理量或现有可用特征识别“运行中 / 非运行中”状态。
- 运行态识别应优先复用当前实时记录中已经存在的可信信号，不凭空新增生产依赖；默认候选信号包括：
- 帧新鲜度与连续性，如 `is_new_frame`、`data_ts_ms`、`max_data_age_ms` 对应的新帧/旧帧判断。
- 振动或速度代理量，如 `Ax/Ay/Az`、`Gx/Gy/Gz` 及其聚合量 `A_mag`、`G_mag`。
- 若 `vx/vy/vz` 可稳定提供，则允许将 `V_mag` 作为运行态辅助证据，但不能在缺失时导致主流程不可用。
- 温度、单次故障分数或云端返回状态不能反向充当本地运行态切片依据。
- 运行态识别必须足够保守且稳定，不能因为单个尖峰、短时抖动、通信抖动或静止期噪声就误判为一次真实运行。
- 运行段切片不得只依赖单一瞬时阈值；至少应结合“进入运行的连续确认”“退出运行的连续确认”“最短运行时长”“最短静止间隔”这几类约束，避免频繁误切。
- 推荐实现为有限状态机或等价机制，至少区分：`idle`、`entering_run`、`running`、`leaving_run` 四类状态；不要只靠一个布尔开关直接翻转。
- 进入运行判定应依赖滑动窗口内连续高活动证据，而不是某一帧突然升高。
- 退出运行判定应依赖滑动窗口内连续低活动证据，而不是某一帧突然回落。
- 当底层连续出现旧帧、超时帧或明显缺帧时，默认先判为“本次切片质量下降”，必要时终止当前片段并标记低质量，而不是继续假定设备仍在稳定运行。
- 当多个候选信号之间冲突时，默认优先选择更保守的结果，即宁可延后进入/提前退出，也不要把长静止段误包进运行段。
- 当运行过程中出现极短暂停、短时低幅波动或个别缺帧时，系统应优先把它视为同一次运行中的局部波动，而不是直接切成多段。
- 只有在满足运行段完整性要求后，该段数据才允许进入诊断主链路；对边界不清、证据不足的片段，应宁可不判，也不要把静止段和运行段混在一起输出强结论。
- 运行段结果应尽量贴近真实运行区间：开始点不能明显滞后到错过主要起振阶段，结束点也不能大量拖入后续长静止段。
- 运行态切片的默认调参应集中在少量配置对象中统一管理，不应把进入阈值、退出阈值、确认点数、最短时长、合并间隔等参数散落在各处字面值里。
- 只有在识别到运行态后，系统才开始累计本次运行段或有效窗口；当满足最小时长、最少样本数和基础质量约束后，才允许进入主判断链路。
- 一次运行结束后，边缘侧应将该次运行对应的数据段固化为可复盘文件或等价结构，并生成本次运行的摘要结果。
- 若一次运行段过短、样本数不足或质量不足，边缘侧应输出“本次运行数据不足”之类的保守结果，而不是强行生成异常结论。
- 静止期数据可用于设备在线性、心跳、基础健康监控或基线维护，但默认不直接触发用户可见的故障判断。
- 边缘设备负责：
- 传感器读取与帧过滤。
- 运行态识别、运行段切片和有效窗口组织。
- 在线异常检测、规则判断、风险计算或复用现有诊断算法的本地执行。
- 本地健康状态、告警事件和可选上下文文件生成。
- 本地缓存与上送重试。
- 云端服务负责：
- 接收边缘上送的结构化状态和上下文。
- 按 `elevator_id` 聚合最新状态、最近告警和事件详情。
- 基于边缘结果生成报告上下文、Markdown 报告草稿和 Dify 输入。
- 为 Dify 或上层系统提供统一查询 API。
- 云端服务在生产模式下不直接依赖 `data/captures`、`data/diagnosis` 等本地采集目录作为当前状态真值来源。
- Dify 调用应从边缘 `monitor` 侧移出默认主链路；生产模式下由云端 API/工作流侧统一对接 Dify。
- 若保留边缘侧直接触发 Dify 的兼容代码，其默认配置应关闭，避免边缘设备承担 LLM 编排职责。
- 当前兼容字段如 `primary_issue`、`top_candidate`、`candidate_faults`、`watch_faults`、`risk`、`report_markdown_draft` 应继续可被云端工作流消费，不因部署拆分破坏契约。
- 离线 CSV 诊断、波形图生成和报告渲染能力继续保留，但它们属于“调试/人工分析能力”，不应再被文档或默认工作流描述成生产主流程。
- 边缘与云端之间的数据同步应优先传输结构化摘要；只有在告警复核需要时才上传上下文 CSV 或压缩内容，避免把云端重新变成原始数据主处理端。
- 训练、模型发布和实验性脚本不纳入本次部署拆分主流程，除非仅需做最小兼容改动。

## 验收标准
- 边缘设备在云端不可达时仍能持续完成本地采集和计算，产生的 heartbeat、alert、context 可进入本地队列，网络恢复后可自动补传。
- 当电梯长时间静止时，系统不会因为固定时刻采样而误生成“有效运行诊断结果”；静止数据最多只进入心跳/健康监控链路。
- 当电梯发生一次满足时长和样本约束的实际运行时，边缘侧能够自动识别该运行段、完成一次诊断并固化段结果。
- 当存在短时冲击、静止期抖动、短暂停顿或个别缺帧时，运行段切片仍能保持稳定，不会轻易误切成多段或把静止段误并入运行段。
- 对人工标注为一次运行的样本，切片结果在起止边界上应保持工程上可接受的误差范围；若边界证据不足，系统应返回保守结果而不是冒充高质量运行段。
- 在缺少 `V_mag` 等可选字段时，系统仍能仅基于现有加速度/角速度活跃度和新帧连续性完成运行态判断，不会因为某个辅助字段缺失而失效。
- 云端在不访问本地采集目录、不运行 `batch_diagnosis` 定时任务的情况下，仍可基于边缘上送结果返回某台电梯的最新状态、最近告警和事件详情。
- Dify 或等价上层工作流默认通过云端 `latest-status/report` 接口读取边缘计算结果，不再依赖边缘直接调用 Dify。
- 部署文档与 Compose 配置能够明确区分云端职责和边缘职责，不再把云端描述为生产主数据处理节点。
- 现有用户可见结果字段保持兼容，部署拆分后不会破坏 `status`、`primary_issue`、`top_candidate`、`watch_faults`、`risk`、`report_markdown_draft` 等核心输出。

## 测试用例
- 新增测试：边缘侧生成 heartbeat/alert/context 后，在云端暂时不可用时写入本地同步队列，恢复后能够成功补传。
- 新增测试：当输入为长时间静止段时，边缘侧不会把该段数据固化为有效运行诊断结果。
- 新增测试：当检测到一次完整或近完整运行过程时，边缘侧能够正确切出运行段，并基于该段生成摘要结果。
- 新增测试：当一次运行段样本过少、时长过短或质量不足时，边缘侧返回低质量/不可判定结果，而不是强行报异常。
- 新增测试：当静止期出现单次尖峰、短时抖动或少量异常帧时，不会误触发一次新的运行段。
- 新增测试：当同一次运行中出现极短暂停或局部低幅区间时，系统不会错误切成多个运行段。
- 新增测试：对带人工标注起止区间的样本，运行段识别结果在约定误差范围内；超出范围时必须以测试失败暴露，而不是静默放过。
- 新增测试：当 `V_mag` 等辅助字段缺失时，运行态识别仍能基于 `A_mag/G_mag` 与新帧连续性稳定工作。
- 新增测试：当连续出现旧帧、过期帧或明显缺帧时，系统会把当前片段标记为低质量或提前终止，而不是继续输出高质量运行段。
- 新增测试：云端 `ingest` 接收到边缘 heartbeat/alert 后，可正确更新指定 `elevator_id` 的 `latest_status`，且无需依赖本地 `batch_diagnosis` 输出文件。
- 新增测试：云端 `diagnosis-report-latest` 以 ingest 落盘结果为输入时，仍能返回包含兼容字段的报告上下文和 Markdown 草稿。
- 新增测试：生产配置下边缘 `monitor` 默认不主动触发 Dify，Dify 相关工作流改由云端侧接口驱动。
- 新增测试：保留 `rule-engine` / `batch-run` 离线接口能力，但文档和默认工作流不会再把它们作为查询“当前状态”的主来源。

## 非目标
- 不在本次需求中改变钢丝绳、橡胶圈或统一决策层的算法判定标准。
- 不把当前项目拆成多个独立仓库或引入全新的微服务体系。
- 不要求一次性消除所有历史兼容入口。
- 不要求把云端完全变成无状态服务；允许继续使用文件落盘方式保存 ingest 结果。

## 建议默认假设
- 生产环境至少有一个云端 API 服务实例和若干个边缘监控实例。
- 当前“边缘计算”优先复用现有 `monitor`、`risk`、`fault`、`report` 相关逻辑，不要求另起一套新算法框架。
- 若后续需要边缘执行现有 `batch_diagnosis` 或 `report.fault_algorithms.run_all`，优先通过增量编排实现，而不是先重构算法目录。

## 开放问题
- 当前边缘主算希望继续以“实时监控链路”为主，还是改成“边缘定时批诊断”为主，需要你确认优先级。
- 云端是否还需要保留“上传 CSV 后立即生成离线报告”的人工分析入口，如果要保留，建议明确为 debug/admin 能力。
- 单台边缘设备是否只负责一台电梯；如果后续一台边缘设备需要管理多台电梯，接口和本地状态文件路径还需要再细化。
